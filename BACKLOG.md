## Detailed feature specs

### ~~Reschedule appointment~~ ✅ done 2026-05-16
`PATCH /appointments/:id/reschedule` — SUT + UI + тесты полностью готовы. `appointments.reschedule.test.ts` написан 2026-05-16, 8/8 тестов зелёные. Нашёл и исправил SUT баг B-07 (неправильный порядок операций в транзакции — тест с waitlist-пациентом поймал, 7 тестов без waitlist пропустили).

**State machine:** `pending` / `confirmed` → reschedule → always `pending` (doctor must re-confirm). Atomic: free old slot + promote waitlist + book new slot.

**Error codes:** `SLOT_TAKEN` (409), `DOCTOR_MISMATCH` (422), `SAME_SLOT` (422), `INVALID_TRANSITION` (422), `SLOT_NOT_FOUND` (404).

**Test plan:**
- 200 reschedule from `pending` → new slot, status `pending`
- 200 reschedule from `confirmed` → status resets to `pending`
- 409 new slot already taken
- 422 reschedule `cancelled` appointment
- 422 new slot belongs to different doctor
- 422 same slot as current
- 403 patient does not own appointment
- waitlist cascade: old slot freed → waitlist patient promoted
- UI: Reschedule button visible for pending/confirmed only
- UI: successful reschedule refreshes list

### ~~COMPLETED appointment status~~ ✅ done 2026-05-15
`PATCH /appointments/:id/complete` — doctor-only terminal transition from `confirmed`.

**Key design:** slot NOT freed (visit occurred); waitlist NOT promoted; patient notified via WS + webhook.

**Test plan — Tier 1:**
- `confirmed → completed` → 200, `status: "completed"`
- Slot stays unavailable after complete (guards copy-paste of cancel logic)
- Waitlist NOT promoted after complete (guards accidental `promoteFromWaitlist` call)
- `pending → completed` → 422 `INVALID_TRANSITION`
- `completed → completed` → 422 (double-click)
- Wrong doctor → 403 (IDOR)
- Patient calls `/complete` → 403 (RBAC)

**Test plan — Tier 2:**
- WS: patient receives `appointment.completed` event
- E2E: completed appointment shows no action buttons in patient UI

### Recurring appointments ✅ Done 2026-05-17

SUT done 2026-05-15. `POST /api/v1/appointments/recurring` + `PATCH /api/v1/appointments/series/:seriesId/cancel`.

**Design:** `seriesId` (UUID) on each appointment; weekly pattern; partial booking model.

**API — `tests/api/appointments.recurring.test.ts` (9 tests, all green):**
- `POST /recurring` — 201 books 2 weekly slots, returns seriesId @smoke
- `POST /recurring` — 201 partial: one slot unavailable → bookedCount=1, unavailable[0].slotId correct
- `POST /recurring` — 404 SLOT_NOT_FOUND for non-existent startSlotId
- `POST /recurring` — 400 VALIDATION_ERROR for unsupported slotPattern ("daily")
- `POST /recurring` — 400 count below minimum (count=1)
- `POST /recurring` — 400 count exceeds maximum (count=13)
- `POST /recurring` — 401 without authentication
- `PATCH /series/:seriesId/cancel` — 200 cancels series, frees all slots @smoke
- `PATCH /series/:seriesId/cancel` — 404 SERIES_NOT_FOUND for unknown seriesId

**Finding:** `INVALID_PATTERN` in repository layer is dead code — route validates `slotPattern` first and returns `VALIDATION_ERROR`. Recorded as DEAD-01 in KNOWN_ISSUES.md.

**UI — `tests/ui/appointments.recurring.ui.test.ts` (4 tests × 2 browsers = 8, all green):**

- cancel-series button shown only for pending/confirmed with seriesId
- cancel series via UI: confirm dialog → list reloads → toast "Series cancelled."
- API error shows inline notice "Couldn't cancel the series"

**Finding during UI test:** default sort on page is `id-desc` ("Newest first") — test must account for DOM order ≠ API response order. Recorded as SORT-01.

**E2E — `tests/e2e/appointments.recurring.e2e.test.ts` (2 tests, all green):**

### Pagination — `GET /appointments/my` + `GET /appointments/doctor`
SUT done 2026-05-15. `?page=&limit=` (page ≥ 1, limit 1–100); response `{ data, total, page, limit, totalPages }`.

**API test plan — `tests/api/appointments.pagination.test.ts` (@api):**
- `GET /appointments/my` no params → 200 `{ data[], total, page:1, limit:20, totalPages }` shape valid @smoke
- `GET /appointments/my?page=1&limit=5` → returns max 5 items; `totalPages = ceil(total/5)`
- `GET /appointments/my?page=2&limit=1` → returns second item (correct offset); off-by-one in `OFFSET=(page-1)*limit` shows wrong appointments
- `GET /appointments/my?limit=0` → 400 `VALIDATION_ERROR` (division by zero → `totalPages: NaN/Infinity`)
- `GET /appointments/my?page=0` → 400 `VALIDATION_ERROR` (negative OFFSET)
- `GET /appointments/my?page=abc` → 400 `VALIDATION_ERROR` (NaN in OFFSET)
- `GET /appointments/doctor` no params → 200 paginated response (doctor JWT) @smoke
