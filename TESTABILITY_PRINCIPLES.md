# Testability Principles — clinic-booking SUT

Это не список правил написанных заранее.
Каждый принцип появился из конкретного момента когда без него стало больно.

---

## 1. Reset endpoint

**Что:** `POST /api/v1/test/reset` — восстанавливает БД до начального состояния за один запрос.

**Зачем:** тесты ломают данные. Без reset — либо пересоздавать БД между прогонами, либо писать сложный teardown для каждого теста. С reset — `beforeEach` в одну строку там где нужен чистый стейт.

**Что это даёт:** тесты изолированы друг от друга без дорогого teardown. Прогон можно повторить в любом порядке.

---

## 2. Специфичные errorCode в теле ответа

**Что:** каждый ошибочный ответ содержит поле `errorCode` — строковый идентификатор (`SLOT_TAKEN`, `INVALID_STATUS`, `NOT_FOUND`, `FORBIDDEN`).

**Зачем:** HTTP статус-код не достаточно точен для ассертов. `403` может означать "нет прав" или "ресурс не существует" — смотря как реализован endpoint. `errorCode` делает намерение однозначным.

**Что это даёт:** тесты проверяют бизнес-логику, а не HTTP-конвенции. Когда порядок проверок в роуте меняется — тест это видит.

---

## 3. RBAC с готовыми ролями из коробки

**Что:** SUT запускается с pre-seeded пользователями: пациент, врач, админ — с известными credentials.

**Зачем:** если тест должен создавать пользователей сам — это дополнительный шаг, дополнительная зависимость, дополнительная точка отказа. Роли уже есть → тест фокусируется на том что тестирует.

**Что это даёт:** тесты на RBAC и ownership пишутся без setup-бойлерплейта. `loginAs('patient')`, `loginAs('doctor')` — и сразу к сценарию.

---

## 4. DB-level unique constraints

**Что:** на уровне БД стоит constraint `idx_appointments_one_active_per_slot` — только один активный appointment на слот.

**Зачем:** race condition на бронировании можно было предотвратить только на уровне приложения — проверить перед записью. Но это не атомарно. Constraint гарантирует что второй `INSERT` упадёт с ошибкой вне зависимости от тайминга.

**Что это даёт:** race condition тестируется детерминированно через `Promise.all`. Тест не проверяет "может случиться" — он проверяет "система это предотвращает".

---

## 5. Стейт-машина appointments с явными переходами

**Что:** appointment проходит чёткие статусы: `pending → confirmed → completed / cancelled`. Переходы которых нет — возвращают `INVALID_STATUS`.

**Зачем:** без явной стейт-машины граничные случаи становятся undefined behavior. "Что если подтвердить уже отменённый приём?" — без стейт-машины это либо молча проходит, либо падает непредсказуемо.

**Что это даёт:** каждый переход тестируется отдельно. Тест на невалидный переход — это один вызов с ожидаемым `INVALID_STATUS`.

---

## 6. Изолированные фикстуры с автоматическим teardown

**Что:** каждая фикстура создаёт ровно то что нужно тесту и убирает после себя через `try/finally`.

**Зачем:** shared state между тестами — главная причина flaky tests. Если тест оставляет данные — следующий тест работает в непредсказуемом окружении.

**Что это даёт:** тесты можно запускать в любом порядке и параллельно. Упавший тест не ломает следующий.

---

## 7. OpenAPI spec как контракт

**Что:** `openapi.yaml` живёт в репо и поддерживается в синхронизации с роутами. Contract drift guard тест проверяет что каждый endpoint задокументирован.

**Зачем:** без spec тест на "правильный shape ответа" — это assertion написанный по памяти. С spec — assertion генерируется из источника истины.

**Что это даёт:** contract drift guard ловит когда добавляется endpoint без документации. Студент видит паттерн: спека — не документация для людей, а машиночитаемый контракт.

---

## 8. Buggy branch

**Что:** отдельная ветка с 12 намеренными багами — по три на каждый уровень (unit/integration/system/security).

**Зачем:** тесты написанные только против правильной реализации не доказывают что они что-то проверяют. Buggy branch показывает: упадёт ли тест если система сломана?

**Что это даёт:** студент видит разницу между "тест зелёный" и "тест что-то проверяет". CI зелёный на buggy branch — это сигнал что покрытие неполное.

---

## 9. Lazy cleanup для token blacklist

**Что:** `tokenBlacklistRepository.js` метод `invalidate()` сначала запускает `DELETE WHERE createdAt < datetime('now', '-2 hours')`, потом вставляет новую запись.

**Зачем:** первый инстинкт — scheduled job или TTL для очистки устаревших токенов. Но это отдельный процесс, отдельная точка отказа, несоразмерная сложность. Access token живёт 1 час → 2 часа безопасный margin. Cleanup coupling с write-путём = нагрузка очистки автоматически пропорциональна нагрузке записи.

**Что это даёт:** тест на session invalidation (`POST /auth/logout → повторный запрос с тем же токеном → 401`) работает без дополнительной инфраструктуры. Cleanup прозрачен для тестов.

---

## 10. Defence in depth: два теста на одну угрозу

**Что:** security suite содержит два независимых теста на сценарий утечки токена — тест на logout (токен должен стать невалидным) и тест на IDOR (чужой токен не даёт доступа к чужим данным).

**Зачем:** тест на logout проверяет кнопку. Тест на blacklist проверяет что украденный токен бесполезен после logout. Один сценарий угрозы — два независимых барьера. Если один обходится — второй держит.

**Что это даёт:** студент видит разницу между "функция работает" и "угроза закрыта". Два теста на одну угрозу — это не дублирование, это defence in depth.

---

## 11. Mock mode как детерминированный unit test для retrieval layer

**Что:** AI recommendation endpoint поддерживает `AI_MOCK_RESPONSE=true` — в этом режиме SUT возвращает top-1 результат retrieval напрямую, без вызова Claude.

**Зачем:** в многослойной AI системе (retrieval → LLM → response) тест может пройти по неправильной причине. Retrieval вернул не ту специальность, но Claude исправил — тест зелёный, баг скрыт. Mock mode убирает LLM из уравнения: если retrieval возвращает не то — тест сразу падает с 422 или неверной специальностью. Claude не компенсирует retrieval ошибку.

**Что это даёт:** CI с `AI_MOCK_RESPONSE=true` стал бесплатным regression тестом для retrieval layer. Именно так был обнаружен RAG-08: "itchy" не матчит keyword "itching" — нашёл CI, не code review и не разработчик.

**Скрытая ловушка:** тест-дата нужно проектировать под алгоритм, а не под семантику. "Itchy red spots" медицински означает Dermatologist, но retrieval этого не знает — он знает только точные строки из knowledge base. Semantic correctness ≠ algorithmic correctness.

---

## Общий паттерн

Ни один из этих принципов не был в дизайн-документе с самого начала.

- Reset endpoint появился когда teardown стал занимать больше строк чем сам тест.
- errorCode появился когда `403` означал три разные вещи в трёх разных роутах.
- DB constraint появился когда стало ясно что application-level check не даёт детерминированный тест на race condition.

Testability — это не фаза проектирования. Это сигнал от тестов о том что система сопротивляется проверке.
