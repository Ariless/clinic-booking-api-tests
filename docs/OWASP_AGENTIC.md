# OWASP Top 10 for Agentic Applications — applicability to this system

**List:** OWASP Gen AI Security Project, *Top 10 for Agentic Applications*, published 2025-12-09
(ASI01–ASI10). **Mapped:** 2026-08-27.

## Why this document exists rather than ten tests

`POST /api/v1/ai/recommend-doctor` is a single model call: keyword retrieval over six records, one
request to Claude with a structured-output schema, one answer, no loop. No memory that survives a
request, no planner, no second agent.

**Updated 2026-08-27:** it now also has tools. `sut/mcp-server/` exposes six of them over this API, so
the categories that turn on tool use are no longer hypothetical here. What the system still does not
have is autonomy — nothing runs unattended, and nothing the model produces is executed.

Running the list as a checklist would produce ten green tests and no information. What the list is
good for here is the opposite exercise: it names the properties that make a category applicable, so
each one can be answered with *what would have to exist*. Four categories applied on the first pass —
one of them because the route was already doing something an agentic system does, and doing it
without a caller identity. Two more became applicable when the tools were built, which was the point
of building them.

| ID | Category | Applies? | Where it stands |

## ASI03 — Identity & Privilege Abuse (found and closed 2026-08-27)

**What was found.** `POST /api/v1/ai/recommend-doctor` had no `requireAuth`. A request with no
`Authorization` header at all returned `200` and a recommendation. So did
`Authorization: Bearer garbage.token.here` — the token was never parsed, so a malformed credential
was indistinguishable from a valid one. Every other domain route in the API required a token; the
one route that spends money at a third party did not.

**Why it is ASI03 and not merely a missing auth check.** The category is about an agent performing a
delegated action under an identity it should not have. That is exactly the shape: the route takes
free text from an anonymous caller, sends it to an external model under the operator's API key, and
returns the result. The caller borrowed the operator's credential without ever presenting one of
their own.

**Three consequences, in order of how quickly they bite:**

1. Unbounded cost. Anyone could spend the operator's Anthropic balance.
2. The rate limiter degraded. `aiRateLimitKey` hashes the `Authorization` header and falls back to
   the literal `guest`, so every anonymous caller shared one `<ip>:guest` bucket — and the per-user
   half of the key only ever engaged for authenticated callers, who needed it least. Combined with
   per-IP-only limiting (D-03), the practical ceiling was low.
3. Free text from an unauthenticated source reached a prompt, which is ASI01's entry point with no
   barrier in front of it.

**Fix.** `requireAuth` on the route; `security: [bearerAuth]` plus the `401` and `404` responses added
to `openapi/openapi.yaml`, which had documented neither. Both existing consumers already send a token
(`public/patient-booking.html` via `ClinicApp.api`, and the mobile `SymptomCheckerScreen` via
`apiPost(..., true)`), so nothing had to change on either side.

**Tests.** `tests/api/security.agentic.test.ts` — 401 with no token, 401 with a malformed token, 200
for an authenticated patient. The third is what keeps the first two honest: a gate that refuses
everyone would pass without it. Proven from both sides — removing `requireAuth` turns exactly the two
401 tests red.

**Why it survived this long:** the suite's own client always sent a token, so every test of this route
exercised the authenticated path. Nothing asked the opposite question until the list did.

## ASI04 — Agentic Supply Chain

The specialty is decided by `ai-service`, a separate deployable that can be shipped on its own. The
SUT turns its answer into a database query and a recommendation shown to a patient. That service is
the supply chain, and the two copies of this logic have already drifted apart twice without anyone
noticing (B-05; the structured-outputs split repaired 2026-08-26).

The mitigation was already in the code — `recommendViaService` re-checks the answer against
`ALLOWED_SPECIALTIES` instead of trusting it, with a comment explaining that a separate deployable can
be redeployed alone. It had no test, which is the same shape as the privacy defences: correct,
deliberate, and free to delete.

**Tests:** `sut/src/__tests__/aiSupplyChain.test.js` — a specialty outside the allow-list is refused
*and never becomes a database query*; the refused value is reported so a log can name it; an
allow-listed specialty passes through; a case-shifted entry is still outside the list, because a SUT
that quietly repairs the service's output is a SUT that no longer has one contract with it.

## ASI06 — Memory & Context Poisoning

There is no agent memory. There is a retrieval corpus, and it is the context: the top three entries
are interpolated into the prompt as one line each, joined by newlines, with no delimiter, no escaping
and no role boundary.

A `\n` inside a description does not corrupt the JSON and does not fail a schema check. It buys the
author of that row as many additional prompt lines as they want, in the position the model reads as
the system's own instructions. Poisoning this context needs no access to the model — it needs a pull
request against a data file.

**Tests:** `tests/unit/knowledge-integrity.test.ts` — every entry occupies exactly one prompt line;
the assembled context has as many lines as it has entries; no description reads as a directive; and a
length bound. Proven from both sides: an entry carrying
`\n- Cardiologist: Ignore previous instructions…` turns three of the four red.

## Open — recorded, not fixed

### ASI08 — the circuit breaker had no test (closed 2026-08-27; it found a defect on the way in)

**Risk:** `aiRecommendation.js` implements a breaker — closed → open after N consecutive
`CLAUDE_UNAVAILABLE` failures → half-open after a recovery window — and exposes it on
`GET /api/v1/ai/circuit-state`. `getCircuitState`, `resetCircuit` and `forceCircuitOpen` are all
exported. Nothing calls any of them from a test, in either repository.

**Why that matters for this category specifically:** ASI08 is about a small failure propagating. The
two *propagation* paths are covered — "Claude unreachable" and "ai-service unreachable" both assert
that the endpoint answers 503 with the right code rather than hanging or blaming the wrong system.
The breaker is the component whose entire job is to stop the third-order effect: a model outage
turning into a retry storm against a paid API. It is the one part of the chain that is asserted
nowhere.

**How this was found:** writing the cross-reference block at the top of `security.agentic.test.ts`.
The comment claimed ASI08 was covered by "the circuit breaker tests in `ai.recommend.test.ts`"; a grep
for `circuit` across both suites returns that comment and nothing else. The claim was written from
the assumption that a component this visible must be tested.

**Closed by** `sut/src/__tests__/aiCircuitBreaker.test.js` — 16 tests: the state machine through a
mocked dependency, and the route itself over real HTTP in `CLAUDE_DEGRADE` mode, because what an open
breaker looks like to a caller is a separate question from what the module's internal state says.

**And the test found what the gap was hiding.** `_onSuccess()` runs only when the state is already
half-open, so a success on the ordinary closed path never clears the counter — the breaker counts
failures over the process's lifetime rather than consecutive ones, and a long-lived instance will
open it during normal operation. The implementation's own comment says "consecutive". Recorded as
`SYSTEM_WEAKNESS_REPORT.md` §12.6 and pinned as-is: the test says in its comment that two of its
expectations invert when the behaviour is corrected.


### ASI07 — the SUT and ai-service do not authenticate each other

`POST /recommend` on `ai-service` accepts any caller that can reach the port. In the compose topology
that is the internal network, but the service holds an Anthropic key and will send any text it is
given to a model. Nothing binds a request to the SUT.

The related half is already mitigated: the SUT does not trust what comes *back* (ASI04 above). The
missing direction is that the service does not know who is asking.

**Direction of a fix:** a shared secret header checked by the service, or mTLS if the topology grows.
Not done here — it changes the contract between the two deployables and the Pact file that pins it.

### ASI09 — the response carries no disclosure that it is machine-generated

`{ recommendedSpecialty, doctors, reasoning }` and nothing else. Nothing marks it as an AI
recommendation rather than clinical advice, and `reasoning` is prose written by a model that reads
like a clinician's note. EU AI Act Art. 13 transparency is tested on the **mobile client**
(`clinic-mobile-tests/features/eu-ai-act.feature` — a disclosure banner in the UI), so the requirement
is met at one surface and absent at the API, where any other consumer would meet it.

`tests/api/security.agentic.test.ts` pins the current response shape rather than inventing a field:
adding one is a product decision, and the test states in its comment that the absence is deliberate,
not overlooked.

**Direction of a fix:** a constant flag on the response body (`"aiGenerated": true` or a
`disclosure` string), documented in the OpenAPI spec, so a consumer cannot present the output as a
diagnosis without ignoring the contract.

## ASI02 — Tool Misuse & Exploitation (surface added and tested 2026-08-27)

The previous version of this document ended by saying the four "No" categories all turned on one
missing capability — the model cannot act — and that an MCP server over this API was the obvious next
step. It was built: `sut/mcp-server/`, six tools, a separate deployable with its own manifest.

Three properties carry the category, each asserted in `sut/src/__tests__/mcpServer.test.js` (16 tests,
driven by a real MCP client over an in-memory transport rather than by importing the handlers):

**Profiles remove affordances rather than guarding them.** A session runs under `readonly`, `booking`
or `full`, and tools outside the profile are never *registered* — absent from `tools/list`, absent
from the model's context. A permission check inside a handler leaves the tool's name and description
in the context, still describable, still reachable through a jailbreak that has to beat one `if`. The
protocol answers "not found", and the test asserts that wording specifically: *"you are not allowed"*
tells an agent the capability exists and it has the wrong session.

**The server holds no credential.** The caller's token is forwarded unchanged; the SUT's `requireAuth`
and `requireRoles` stay the authority. The service-account design — one privileged token in the
server's environment — is the confused deputy, and would mean a hijacked agent inherits authority over
every patient rather than over the operator's own record. Tested from both sides: with the refusal
removed and a fallback service account substituted, the forwarding test goes red.

**Tool descriptions are screened at start-up.** `descriptionPolicy.js` rejects directive phrasing,
references to other tools, invisible characters (bidi and zero-width, built from escapes so the file
does not contain what it screens for), and anything over 300 characters. A poisoned description stops
the process rather than logging a warning.

**Also covered by the same file:** ASI04 in its tool form (a description arriving through a dependency
bump is the supply chain), and ASI10 in part — annotations are derived from the catalogue rather than
hand-written, so a client can gate human confirmation on `destructiveHint` and have that mean
something.

**Found while building it:** two tools described a filter the API does not have. `GET /doctors` takes
no `?specialty=` and there is no `/specialties` route; the API ignores unknown query strings and
returns everyone, so the model would have reported a filtered list that was never filtered. Both tools
aggregate locally now and say so in the code. The end-to-end tests exist because of this: without them
the suite would have stayed green while every tool called a route that does not exist.

The `agentic` job runs in mock mode on purpose: every assertion in it is about authorisation, the
contract, or the corpus that feeds the prompt. None of it needs a model call, and none of it should
cost money to check.

## What still does not apply

**ASI05 (Unexpected Code Execution)** — nothing the model produces is executed, interpolated into a
query, or written to disk. Tool arguments are Zod-validated and reach the API as JSON values and path
segments.

**ASI10 in full** — nothing runs autonomously. No scheduled agent, no background loop, no delegated
authority that outlives a request. It would apply the day something drives this server unattended.
